# Timeline klipów – plan wykonania

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Kolejka klipów z biblioteki. Każdy klip ma własny graf efektów, fragment od–do w pętli i czas. Przejście do następnego wypada na beat po upływie czasu. Kolejkę da się edytować na żywo.

**Architecture:** Czyste operacje na kolejce są w `src/shared/timeline.ts`, a ich stan trzyma `AppStore` w procesie głównym, który zapisuje go na dysk i rozsyła. Okno Visualizera liczy czas i beat (`Sequencer`), pilnuje pętli fragmentu (`VideoPool`) i przez IPC `front:timeline-next` prosi o następny element. Panel edytuje kolejkę komunikatami WS.

**Tech Stack:** Electron 44, TypeScript, React 19 + Zustand (panel), Three.js + postprocessing (renderer), Vitest.

**Spec:** `docs/superpowers/specs/2026-11-14-timeline-design.md`

## Global Constraints

- Renderer i panel nie importują electron ani Node. Okno Visualizera komunikuje się tylko przez `window.api` z preload.
- Wszystko, co przychodzi z zewnątrz, waliduje `protocol.ts` i `sanitizeTimeline`. Nie luzujemy kontroli w `server.ts`, nie wyłączamy `contextIsolation` ani `sandbox`, nie zmieniamy CSP.
- W pętli rAF nie wolno alokować.
- Wartości: `duration` od 1 do 600 s, domyślnie 16. `waitBeat` domyślnie true. Gdy beatu brak, cięcie najpóźniej 4 s po czasie elementu. `inPoint` ≥ 0, domyślnie 0. `outPoint` > `inPoint` + 0,1 s, w przeciwnym razie `null`, co oznacza „do końca”. Po ostatnim elemencie kolejka wraca na początek.
- Bez grającego timeline'u aplikacja działa dokładnie jak dziś.
- Każde zadanie kończy się przejściem `npm run typecheck`, `npm run lint`, `npm test` i Prettiera.

## Review Focus

1. Kolejne elementy mają ten sam klip, a inny fragment: wideo musi przewinąć do nowego `inPoint`, choć adres pliku się nie zmienia. Test w zadaniu 4: `VideoPool.setRange` z tym samym URL przewija.
2. Klip usunięty z biblioteki w trakcie grania: przejście go pomija. Gdy w kolejce nie ma żadnego istniejącego klipu, timeline się zatrzymuje, a nie kręci w kółko. Test w zadaniu 1: `nextIndex`.
3. Usunięcie albo przesunięcie elementu, który właśnie gra, nie może zmienić tego, co widać. Indeks bieżącego elementu musi iść za nim, a po usunięciu wskazywać na następny. Testy w zadaniu 1.
4. Cisza w secie: z `waitBeat` cięcie następuje najpóźniej 4 s po czasie elementu. Test w zadaniu 3.
5. Node Wideo ze stałym plikiem w grafie elementu nie może wygrać z klipem z kolejki, gdy timeline gra. Test w zadaniu 4: `pickVideoId`.

### Task 3: Zegar cięć (`Sequencer`)

**Files:**

- Create: `src/renderer/src/engine/timeline.ts`
- Test: `src/renderer/src/engine/timeline.test.ts`

**Interfaces:**

- Produces:
  - `class Sequencer { step(dt: number, beat: boolean, item: { id: string; duration: number; waitBeat: boolean } | null): boolean }`
  - `step` zwraca true dokładnie raz na element, w chwili, gdy trzeba ciąć. Potem zwraca false, dopóki `item.id` się nie zmieni. Zmiana `id`, na przykład po cięciu albo `goto`, zeruje licznik. Przy `item === null` zeruje licznik i zwraca false.
  - `beatTriggered(beat: number): boolean`: true, gdy obwiednia beatu z `AudioLevels.beat` jest ≥ 0,99, bo `BeatDetector` ustawia 1 dokładnie w klatce uderzenia.

- [ ] **Step 1: Testy, które padają**
  - Bez `waitBeat`, przy `duration 2` i krokach 1/60: true w kroku 120 (±1), wcześniej false.
  - Z `waitBeat`: po 2 s bez beatu wynik dalej false. Pierwszy beat po 2 s daje true. Beat przed upływem 2 s niczego nie wyzwala.
  - Z `waitBeat` i ciszą: true po 2 + 4 s (`beatGrace`), ±1 krok.
  - Po true kolejne kroki z tym samym `id` dają false. Nowe `id` zaczyna odliczanie od zera.
  - `beatTriggered(1)` daje true, `beatTriggered(0.92)` daje false.

      Oczekiwane: FAIL.

- Test: `src/renderer/src/engine/timeline.test.ts`, `src/renderer/src/engine/video/VideoSource.test.ts`

**Interfaces:**

- Consumes: `Sequencer` i `beatTriggered` (zadanie 3), `Timeline` (zadanie 1), `FrontApi.timelineNext` (zadanie 2).
- Produces:
  - `loopTarget(time: number, fileDuration: number, inPoint: number, outPoint: number | null): number | null`: zwraca czas, do którego przewinąć, albo `null`. Koniec fragmentu to `min(outPoint ?? fileDuration, fileDuration)`. Gdy `time >= koniec − 1/120` albo `time < inPoint − 0,25`, zwraca `inPoint`. Gdy `inPoint >= fileDuration`, traktuje `inPoint` jak 0.
  - `pickVideoId(state: AppState, sourceFixedId: string | null): string | null`: gdy timeline gra i bieżący element ma klip z biblioteki, zwraca `item.videoId`. W przeciwnym razie zachowuje się jak dziś (stały plik z node'a, jeśli istnieje w bibliotece, inaczej `activeId`).
  - `VideoPool.setRange(inPoint: number, outPoint: number | null, restart: boolean): void`. Zapamiętuje zakres. Przy `restart` przewija aktywne wideo do `inPoint`. Nowo ładowany slot startuje od `inPoint`, ustawionego w `loadedmetadata` przed `play()`.
  - `VideoPool.enforceRange(): void`: wołane co klatkę. Korzysta z `loopTarget`. Bez zakresu, czyli poza timeline'em, nic nie robi. W trybie zakresu `video.loop` musi być false, żeby pętlę robił `enforceRange`, a nie przeglądarka.
  - `Engine` przyjmuje w konstruktorze `onTimelineNext: () => void`. Gdy timeline gra, w `frame` woła: `sequencer.step(dt, beatTriggered(levels.beat), bieżącyElement)`, a przy true wywołuje `onTimelineNext()`. W `setState`, przy zmianie id bieżącego elementu, woła `pool.setRange(item.inPoint, item.outPoint, true)`. Gdy kolejka stoi, zakres jest czyszczony.
  - `App.tsx` przekazuje `() => window.api.timelineNext()`.
